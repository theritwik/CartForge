# CartForge Security and Reliability Review

Carried out for Milestone 10 on 2026-11-20, against the code on `main` after Milestone 9. Each area lists what was checked, the result, and the evidence: tests or code. Findings that were fixed have regression tests; accepted risks are stated with their reason.

## Findings fixed

## Checklist

| Area                                 | Result                | Evidence                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ------------------------------------ | --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Password storage                     | Pass                  | Argon2id with OWASP parameters, rehashed on login when the parameters change (`password.ts`). Unknown emails are verified against a decoy hash, so they take as long to reject as a wrong password                                                                                                                                                                                                                                      |
| Sessions                             | Pass                  | 32-byte random opaque tokens; only the SHA-256 is stored. Idle and absolute expiry; a new token on every login (no fixation); revocation on logout, logout everywhere, and password change (`sessions.ts`, `auth.test.ts`). E2E: an expired session is treated as signed out and its row deleted                                                                                                                                        |
| Cookie settings                      | Pass                  | `HttpOnly`, `SameSite=Lax`, `Path=/`, host-only; `Secure` and `__Host-` in production (`session-cookie.ts`). Verified on the production containers                                                                                                                                                                                                                                                                                      |
| CSRF                                 | Pass                  | Every non-GET `/api` request must carry the web origin in `Origin` (or `Referer`) and, with a body, be JSON, which a cross-site form cannot send (`verify-origin.ts`, tests in each module)                                                                                                                                                                                                                                             |
| Security headers (API)               | Pass                  | Helmet defaults; `X-Powered-By` off; `Cache-Control: no-store` on authenticated routes                                                                                                                                                                                                                                                                                                                                                  |
| Security headers (web)               | Fixed                 | Finding 2. A script `Content-Security-Policy` is not set: it needs per-request nonces on every page                                                                                                                                                                                                                                                                                                                                     |
| Input validation and body size       | Pass, finding 4 fixed | Every body, parameter, query and environment variable goes through a Zod schema. JSON only, 10 KB (32 KB for admin). Unknown fields are stripped, and roles are never read from input                                                                                                                                                                                                                                                   |
| Rate limiting and Redis failure      | Fixed                 | Findings 1 and 3. Limits fail open when Redis is unreachable, logging without the email, password or token (`auth.test.ts`, `rate-limit-writes.test.ts`). Counters are on a Redis instance that never evicts                                                                                                                                                                                                                            |
| Admin authorization                  | Pass                  | `adminRouter` applies `requireAuth` and `requireRole('ADMIN')` to every route. Each endpoint is tested as anonymous (401) and customer (403). Demotion takes effect on the next request. Admins cannot mark orders paid (`order-status-policy.ts`). E2E: a customer gets 404 for `/admin` pages and 403 from the admin API                                                                                                              |
| Cross-user data access               | Pass                  | Carts, orders and payments are queried with the owner in `where`; another customer's resources answer 404 (`cart.test.ts`, `orders.test.ts`, `payments.test.ts`). Users are returned only through `publicUserSelect`                                                                                                                                                                                                                    |
| Inventory consistency                | Pass                  | Reserve, release and commit run in the caller's transaction, as conditional updates in product-id order. A CHECK constraint is the last guard against overselling. Tested: concurrent checkout of the last unit, multi-product rollback, admin adjustments racing checkouts, single release on concurrent expiry and cancellation                                                                                                       |
| Checkout idempotency                 | Pass                  | `Idempotency-Key` is required and unique per customer; the cart lock serialises a customer's checkouts; the client's expected total is compared, never used (`orders.test.ts`). Accepted risk: reusing a key with a different body returns the first order instead of an error                                                                                                                                                          |
| Stripe webhook verification          | Pass                  | Raw body parsed before the JSON parser and outside the origin check; signature verified by the Stripe SDK; invalid signatures answer 400 and change nothing (`payments.test.ts`)                                                                                                                                                                                                                                                        |
| Payment reconciliation and refunds   | Pass                  | Amount, currency, order and session are checked before an order is marked paid. Late, duplicate or mismatched payments become `REFUND_PENDING` and are refunded with an idempotency key, retried until they succeed, and recovered if Stripe forgot the key. Events are recorded in the same transaction as their effects (`payments.test.ts`). Not verified against real Stripe test mode ([stripe-test-mode.md](stripe-test-mode.md)) |
| Error handling and logging           | Pass                  | Central error handler; unexpected errors answer a generic 500 and are logged with the stack server-side only. Request logs redact `Cookie`, `Authorization` and `Set-Cookie`; bodies are not logged; tests check passwords, emails and tokens are absent from rate-limiter and cache failure logs                                                                                                                                       |
| Migrations                           | Pass                  | Forward-only SQL; CHECK constraints and triggers written by hand; CI applies all migrations to an empty database and fails on drift. Procedure and rollback strategy in [deployment.md](deployment.md)                                                                                                                                                                                                                                  |
| Environment configuration            | Pass, finding 6 fixed | Validated at startup. Production requires Stripe test-mode keys and refuses live keys and the simulator. The cache must be a separate Redis from rate limits. `.env` files are git-ignored and excluded from Docker build contexts                                                                                                                                                                                                      |
| Background jobs on several instances | Fixed                 | Finding 5. Order expiry, refund retries and the session sweep were already correct when run concurrently (tested); now they are also coordinated                                                                                                                                                                                                                                                                                        |
| Dependencies                         | Finding 7 fixed       | `pnpm audit`: two moderate advisories remain, both in development-only tools: `uuid` 8 through autocannon (benchmarks; the vulnerable functions are not used), and `minimatch` 10 through ESLint. Neither ships in the API or web images' code paths                                                                                                                                                                                    |
| Development simulator                | Accepted              | Its routes are unauthenticated: the session id in the URL is an unguessable capability, like Stripe's hosted page URL. It is mounted only without a Stripe key, which production does not allow (verified: 404 in the production container)                                                                                                                                                                                             |

## Accepted risks and limitations

- **Account enumeration at registration.** Registering an existing email answers 409. This is the usual trade-off for a clear sign-up error. Registration is limited to 10 per address per hour.
- **No password reset or email verification.** Neither is implemented; there is no email delivery.
- **No script Content-Security-Policy** (see finding 2).
- **Per-address limits depend on the deployment** setting `TRUST_PROXY_HOPS` correctly, and on the web app and API having no public route that bypasses the load balancer.
- **Rate limits fail open** when the rate-limit Redis is down, so an outage does not lock out every user. Alert on "Rate limiter unavailable" log lines.
- **The simulator is not Stripe.** Payment behaviour has been tested with mocks and the simulator only.
